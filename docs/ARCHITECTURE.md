# Private Tasks — Architecture

This document describes **how** Private Tasks is built: its components, data model, API, security, deployment and development process. **What** it does lives in [SPEC.md](SPEC.md), and **why** key decisions were made lives in [adr/](adr/).

## 1. Overview

```
Browser / installed PWA
        │  HTTPS
        ▼
Caddy (optional reverse proxy, automatic TLS)
        │  HTTP, internal Docker network
        ▼
private-tasks container
  ├── FastAPI app: REST API under /api/v1
  └── built React app, served as static files
        │  internal Docker network only
        ▼
PostgreSQL
```

- **One application container.** The FastAPI app serves both the API and the compiled frontend, so an instance is just two containers: the app and the database.
- **Caddy is optional.** Many self-hosters already run a reverse proxy (Traefik, Nginx Proxy Manager...). Caddy is included in the Compose file behind a profile for those who do not.
- **PostgreSQL is never exposed** outside the internal Docker network.

## 4. Backend design

The backend has three layers, and each has one job:

1. **Routes (`api/`)** translate HTTP: parse and validate input with Pydantic, call one service function, return a schema. No business logic.
2. **Services (`services/`)** hold every business rule from SPEC.md section 5: completing with subtasks, undo, moving, ordering, import. They receive a database session and plain values, so they are tested without an HTTP server.
3. **Models (`models/`)** define the tables. No logic beyond column definitions and relationships.

One request is one database transaction: a service either applies all its changes or none.

## 5. Data model

PostgreSQL, four tables. A list has many tasks; a main task has many subtasks (one level).

### 5.1 `lists`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | May be generated by the client |
| `name` | `text` | 1–100 characters |
| `icon` | `text` | Lucide icon name, e.g. `graduation-cap` |
| `color` | `text` | Palette key, e.g. `blue` |
| `position` | `text COLLATE "C"` | Fractional index for sidebar and column order |
| `is_visible` | `boolean` | Default `true` |
| `sort_mode` | `text` | `manual` (default) or `due_date` |
| `source_id` | `text`, nullable, unique | Google list id, for idempotent import |
| `created_at`, `updated_at` | `timestamptz` | UTC |
| `deleted_at` | `timestamptz`, nullable | Soft delete |
| `sync_seq` | `bigint` | Change counter (5.6) |

### 5.2 `tasks`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | May be generated by the client |
| `list_id` | `uuid` FK → `lists` | |
| `parent_id` | `uuid` FK → `tasks`, nullable | Null = main task |
| `title` | `text` | 1–500 characters |
| `description` | `text`, nullable | Up to 10,000 characters |
| `due_date` | `date`, nullable | Wall-clock date (5.5) |
| `due_time` | `time`, nullable | Wall-clock time; null = all-day |
| `starred_at` | `timestamptz`, nullable | Null = not starred |
| `completed_at` | `timestamptz`, nullable | Null = pending |
| `position` | `text COLLATE "C"` | Fractional index within the list or the parent |
| `source_id` | `text`, nullable, unique | Google task id |
| `created_at`, `updated_at` | `timestamptz` | UTC |
| `deleted_at` | `timestamptz`, nullable | Soft delete |
| `sync_seq` | `bigint` | Change counter |

Constraints and indexes:

- `CHECK (due_time IS NULL OR due_date IS NOT NULL)`: no time without a date.
- A subtask cannot have subtasks: validated in the service, because PostgreSQL cannot express it as a simple constraint.
- Indexes on `(list_id, position)`, `(parent_id, position)`, `due_date`, `starred_at` and `sync_seq`. Every query filters `deleted_at IS NULL`.

### 5.3 `settings`

A single row, created on first start.

| Column | Values |
| --- | --- |
| `theme` | `system` (default), `light`, `dark` |
| `language` | `es`, `en` |
| `timezone` | IANA name, e.g. `Europe/Madrid`; initial value from `PT_TIMEZONE` |

### 5.4 `sessions`

| Column | Notes |
| --- | --- |
| `id` | `uuid` PK |
| `token_hash` | SHA-256 of the session token, unique. The token itself is never stored |
| `device_name` | Derived from the User-Agent, e.g. "Chrome on Windows" |
| `created_at`, `last_used_at`, `expires_at` | `timestamptz`, UTC |

The username and password hash are not in the database: they come from the environment (section 7).

### 5.5 Dates and timezones

There are two kinds of dates, and they are stored differently on purpose:

- **Wall-clock dates** (`due_date`, `due_time`) are what the user typed: "Friday, 18:00". They are stored as-is, without converting to UTC, and interpreted with `settings.timezone`. An all-day task on Friday can never drift to Thursday.
- **Instants** (`created_at`, `updated_at`, `completed_at`, `starred_at`, `deleted_at`, session times) record an exact moment and are stored in UTC.

"Today", overdue tasks and relative dates are computed with `settings.timezone`.

### 5.6 Design patterns

- **Nullable timestamps instead of booleans.** `completed_at`, `starred_at` and `deleted_at` say both whether something happened and when, and cannot contradict a separate flag.
- **Soft delete.** Lists and tasks are never removed in v1; `deleted_at` is set instead. This enables undo and, later, propagating deletions to synced devices. Permanent purge of rows deleted more than 30 days ago arrives with sync in v2.
- **Fractional indexing.** `position` is a text key; placing an item between two others generates a key between theirs, without touching other rows. The `"C"` collation makes PostgreSQL compare keys byte by byte, which is what the algorithm requires.
- **Shared action timestamp.** Every row changed by one action gets exactly the same `completed_at` or `deleted_at`. Undo reverts only the rows with that timestamp, so earlier changes are untouched.
- **Change counter.** A PostgreSQL sequence feeds `sync_seq`; every insert or update of `lists` or `tasks` takes a new value. Unlike `updated_at`, it never collides and does not depend on the clock. It is unused in v1 and prepares the v2 sync endpoint.

## 6. API

### 6.1 Conventions

- Base path `/api/v1`. Breaking changes would go to `/api/v2`.
- JSON with `snake_case` fields. `due_date` as `"2026-11-03"`, `due_time` as `"18:00"`, instants as ISO 8601 in UTC.
- Errors always have the same shape, with a stable machine-readable code:

```json
{ "error": { "code": "task_not_found", "message": "Task not found" } }
```

- **Actions with rules have their own routes** (`POST /tasks/{id}/complete`) instead of generic field updates, so the rules live only on the server.
- **Moves send neighbors, not positions:** the client says "between A and B", and the service computes the key.
- **Idempotent creation:** create routes accept an optional client-generated `id`. If a row with that id already exists, the existing row is returned instead of creating a duplicate.
- The interactive OpenAPI documentation is generated by FastAPI at `/api/docs`.

### 6.2 Endpoints

| Method and path | Purpose |
| --- | --- |
| `POST /auth/login` | Username and password; creates a session |
| `POST /auth/logout` | Ends the current session |
| `GET /auth/sessions` | Lists active sessions |
| `DELETE /auth/sessions/{id}` | Ends one session (`all` ends every other session) |
| `GET /health` | Liveness check, no session needed |
| `GET /lists` | All lists with their pending counters |
| `POST /lists` | Create a list |
| `PATCH /lists/{id}` | Change name, icon, color, visibility or sort mode |
| `POST /lists/{id}/move` | Reorder relative to neighbors |
| `DELETE /lists/{id}` | Delete the list and its tasks |
| `GET /lists/{id}/tasks` | Tasks of a list, subtasks nested |
| `POST /lists/{id}/tasks` | Create a task or subtask (`parent_id`) |
| `GET /tasks?starred=true` | Starred view |
| `GET /tasks?from=…&to=…` | Calendar: dated pending tasks of visible lists in a date range |
| `GET /tasks?q=…` | Search by title |
| `PATCH /tasks/{id}` | Edit title, description, date, time or star |
| `POST /tasks/{id}/complete` | Complete the task and its subtasks |
| `POST /tasks/{id}/uncomplete` | Uncomplete following SPEC 5.1 |
| `POST /tasks/{id}/move` | Reorder or move to another list |
| `DELETE /tasks/{id}` | Delete the task and its subtasks |
| `POST /undo` | Undo one action from its `undo_token` |
| `GET /settings`, `PATCH /settings` | Read and change theme, language, timezone |
| `POST /import/google-takeout` | Upload Tasks.json; returns a summary |
| `GET /export` | Download everything as JSON |

### 6.3 Undo tokens

Completing, deleting and moving return an `undo_token`. It is a short-lived token signed with `PT_SECRET_KEY` (HMAC), valid for 60 seconds, that describes the action: its type, the affected ids, the shared action timestamp and, for moves, the previous list, parent and position.

`POST /undo` verifies the signature and expiry, checks that the affected rows have not changed since the action (by `sync_seq`), and reverts it. If something changed in between, it answers `undo_conflict` and changes nothing. Being stateless, it needs no extra table.

## 7. Authentication and security

### 7.1 Credentials

The single user is defined in the environment, not in the database:

| Variable | Content |
| --- | --- |
| `PT_USERNAME` | Username |
| `PT_PASSWORD_HASH` | Argon2 hash, generated with `docker compose run --rm app hash-password` |
| `PT_SECRET_KEY` | Long random key (`openssl rand -hex 32`) used to sign undo tokens |

### 7.2 Sessions

- Login creates a random 256-bit token. Only its SHA-256 hash is stored; a database leak does not reveal usable sessions.
- **Web:** the token travels in an `HttpOnly`, `Secure`, `SameSite=Strict` cookie that page scripts cannot read. State-changing endpoints accept only JSON bodies, which together with `SameSite` protects against CSRF.
- **Mobile app (v2):** the same token in an `Authorization: Bearer` header.
- **Expiry:** 30 days after the last use. `last_used_at` and `expires_at` are refreshed on use, at most once per hour to avoid a write on every request.
- Sessions are revocable one by one or all at once.

### 7.3 Other measures

1. HTTPS everywhere, through Caddy with automatic Let's Encrypt certificates or the user's own proxy. HSTS, CSP and related headers are set in the Caddyfile.
2. Login is limited to 5 attempts per minute per IP (in memory, which is enough for a single process). Failures are logged in a format fail2ban can read. The app trusts `X-Forwarded-For` only from the configured proxy.
3. All input is validated with Pydantic, with explicit length limits and a maximum size for the import file.
4. Logs never contain task or list content: only requests, status codes and errors.
5. No telemetry and no outgoing connections.
6. Dependencies are updated through Dependabot, and CodeQL scans the code.

## 8. Frontend design

- **Server state through TanStack Query only.** Each API resource has a typed hook in `src/api/`. Complete, delete and move use optimistic updates: the interface changes at once, shows the 5-second undo toast, and rolls back if the server rejects the change.
- **Pure helpers in `src/lib/`**, such as relative dates and ordering, are framework-free and unit tested with Vitest.
- **Theme tokens.** Colors, spacing and radii are CSS variables with a light and a dark set; the system theme follows `prefers-color-scheme`. Components never use raw colors.
- **i18n.** Every text goes through react-i18next, with one JSON file per language. Dates are formatted with `Intl` and the user's language.
- **Offline read-only.** The TanStack Query cache is persisted in the browser and the PWA service worker caches the app shell, so the last loaded data is shown without a connection. Mutations are disabled while offline.
- **Accessibility.** Real buttons, inputs and labels, labels on icon-only buttons, visible focus and keyboard-operable drag and drop (dnd-kit supports it).

## 9. Deployment

Reference deployment target: **Ubuntu Server LTS** with Docker Engine and the Compose plugin. Development happens on the maintainer's computer; the server only runs the published image.

### 9.1 Image

A multi-stage `Dockerfile`: the first stage builds the frontend with Node, the second installs the backend with uv on a slim Python image and copies the built frontend in. The app runs as a non-root user.

GitHub Actions builds the image on every version tag and publishes it to GitHub Container Registry for `amd64` and `arm64`.

### 9.2 Compose

`deploy/compose.yml` defines:

- `app`: the Private Tasks image, with a health check on `/api/v1/health`.
- `db`: PostgreSQL with a named volume, only on the internal network.
- `caddy`: optional, enabled with `docker compose --profile caddy up -d`.

Configuration comes from `deploy/.env`, documented in `deploy/.env.example`: the variables in 7.1, the database credentials, `PT_TIMEZONE`, `PT_TRUSTED_PROXIES` (the reverse proxy allowed to set `X-Forwarded-For`) and, for Caddy, `PT_DOMAIN`.

### 9.3 Lifecycle

- **Install:** download `compose.yml` and `.env.example`, fill in `.env`, run `docker compose up -d`.
- **Migrations** run automatically at startup, so updating means changing the image version and restarting.
- **Backups** are not automated. The documentation explains how to schedule `pg_dump` and how to restore; the JSON export is an extra copy.

## 10. Quality and process

### 10.1 Git workflow

- `main` is protected: every change arrives through a pull request, merged only if CI passes.
- Branches by type: `feat/`, `fix/`, `docs/`, `chore/`.
- Squash merge, with Conventional Commits messages, e.g. `feat(tasks): add complete endpoint`.
- The PR template asks what changes, why and how it was tested.
- The maintainer acts as product director: the AI agent develops on local branches, and the director pushes, opens pull requests and merges.

### 10.2 Versioning

- Semantic versioning: `0.x` during development, `1.0.0` when v1 is complete.
- `CHANGELOG.md` in Keep a Changelog format, updated in every pull request.
- A version tag publishes the Docker image and the GitHub release.

### 10.3 Continuous integration

| Area | Checks on every pull request |
| --- | --- |
| Backend | ruff, mypy, pytest against a real PostgreSQL, Alembic migrations in sync with the models |
| Frontend | ESLint, Prettier, TypeScript, Vitest, build |
| Docker | The image builds |
| Security | Dependabot (weekly), CodeQL |

Playwright end-to-end tests run on merges to `main` and before each release.

### 10.4 Tests

- Every business rule in SPEC.md section 5 has a service test.
- Every API route is tested in its normal case and its errors (not found, invalid input, no session).
- Import is tested with sample `Tasks.json` files, including re-import and export round trip.
- Frontend: pure helpers with Vitest; main flows with Playwright (sign in, create, complete and undo, import).
- Every bug fix starts with a test that reproduces it.

### 10.5 Local development

- `compose.dev.yml` runs PostgreSQL only; the API and frontend run on the host with hot reload.
- pre-commit hooks format and lint before each commit.
- `make dev`, `make test` and `make lint` cover daily work.

## 11. Prepared for v2

- **Sync:** `GET /api/v1/sync?since=<sync_seq>` will return changed and deleted rows. Client ids and idempotent creation already exist. Conflicts: the last change to reach the server wins, field by field, since `PATCH` sends only changed fields.
- **Reminders:** a `reminders` table and a background job that sends due reminders to the configured ntfy topic.
- **Native Android app:** Kotlin with Jetpack Compose, a local database, a queue of offline changes and the same API with a Bearer token.
